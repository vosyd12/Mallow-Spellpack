# 전투 기반·슬라임 구현 정리

2026-11-06. 사용자 작성 C# 코드와 AI가 보조한 씬·외형·검증 작업을 현재 파일 기준으로 정리했다. 새 게임 규칙을 확정하는 문서가 아니다. 수치는 조정 가능한 구현값이며 최신 기획은 확정 시 GAME_DESIGN.md에 기록한다.

## 요청과 작업 방식

사용자는 이전의 큰 구현을 잠시 멈추고 직접 이해·수정할 수 있는 현재 프로젝트로 작업을 바꿨다. 게임 방향을 바꾼 것이 아니라 코드 작성의 주도권과 작업 단위를 바꾼 것이다. 사용자가 코드를 작성·수정하고, AI는 설계 제안·관련 코드 검토·요청받은 Hierarchy와 시각 작업을 보조한다. MCP·Notion은 요청한 경우에만 사용한다.

## 현재 연결 구조

| 파일 | 책임과 연결 |
| --- | --- |
| EnemySpawner.cs | Enemy[]에서 Prefab 선택 → Stage.TransformPoint로 위치 변환 → Enemy.Initialize(player) → 생성 목록 등록 |
| Enemy.cs | 추적 대상·초기 스탯·HP 감소·사망. 기본 이동을 끄면 슬라임 이동과 중복하지 않음 |
| SlimeMotion.cs | Prepare → Jump → Land. 루트 Rigidbody2D로 전진하고 Visual 자식으로 높이·압축·복원 표현 |
| Player.cs | 능력치·레벨업 코드·가까운 적 검색·회피. 현재 검색 타이머/씬 연결 결함은 남음 |
| PlayerAttack.cs | 사거리·발사 주기·현재 INT를 반영한 무작위 피해·Bullet 생성. Player.Target 연결은 남음 |
| Bullet.cs | Initialize로 대상/피해 전달 → Rigidbody2D 추적 → 지정 대상 명중 → 피해 후 제거. 수명/대상 소멸 시 제거 |
| LandingDust.cs | 착지 강도에 따른 파티클 속도와 Burst 개수 설정 → 재생 → 완료 콜백에서 풀 반환 |
| LandingDustPool.cs | 씬의 공용 풀. 40개 예열·Get/Release·반환 시 비활성화·보관 상한 64 |
| PlayerState.cs·EnemyState.cs | 개체의 런타임 능력치 데이터. 외부 데이터베이스·저장 기능은 현재 없음 |
| Stage.cs | 현재는 스테이지 번호 필드만 있음. 진행/증가 기능으로 표시하지 않음 |

Stage는 Prefab으로 바닥과 벽을 함께 관리한다. 플레이어·생성 적의 부모는 Stage 바깥에 두어 바닥 확대가 캐릭터 크기까지 바꾸지 않게 했다. Stage 확대·경계·외형의 세부 이력은 문서 목록에서 연결한다.

## 문제와 선택한 해결

### 적 등록 오류를 줄이는 구조

처음 제안한 enum Type + Prefab 쌍은 Small에 Large를 잘못 연결할 수 있었다. 사용자가 이 불일치 위험을 지적해 Enemy[]로 단순화했다. 등록된 Prefab 자체가 외형·동작을 가지며 Spawner는 목록과 위치를 관리한다. Enemy 컴포넌트가 없는 대상을 연결하는 실수를 줄이고 종류명을 중복 입력하지 않는다. 다만 Enemy[]만으로 씬 오브젝트와 Prefab을 엄격히 구분하는 것은 아니다.

Prefab 원본은 씬 Player를 직접 참조할 수 없으므로 생성 후 Initialize로 전달한다. 생성 목록을 List로 보관하고 가까운 적을 조회해 장면 전체를 매 프레임 검색하지 않는 방식으로 연결했다. 배열은 등록 목록, List는 생성된 인스턴스 목록으로 용도가 다르다. 죽은 적은 조회 시 null 확인으로 건너뛴다. 시작 시 한 번 생성하는 현재 범위에는 충분하며 반복 무한 생성/장기 목록 정리는 추가로 구현하지 않았다.

### 슬라임이 통통 뛰지 않는 문제

처음에는 Enemy가 계속 전진하고 SlimeMotion이 외형만 흔들었다. 사용자는 정지·압축·도약 전진·착지 복원의 리듬을 원했다. 또한 이동 감지를 LateUpdate의 프레임별 위치 차이로 판단하면서, 물리 갱신 사이의 렌더링 프레임을 정지로 인식했다. MCP 관찰에서 이동 중 모션 강도가 0.16 → 0.10 → 0.03 → 0으로 줄어드는 것을 확인했다.

이동을 추측하는 가중치를 제거하고 명시적 3상태 FSM으로 바꿨다. FixedUpdate에서 준비·착지는 멈추고 도약 중에만 전진한다. 도약 시작 때 방향을 고정하며 Visual은 사인 곡선으로 오르내린다. 일반 Enemy 이동은 슬라임 Prefab에서 끄고 회전을 고정해 중복 이동과 뒤집힘을 방지했다. 이미지 교체만으로 해결할 문제가 아니었다.

현재 저장값은 다음과 같다. 제안 당시 값과 다를 수 있으며 확정 밸런스가 아니다.

| Prefab | 이동속도 | 준비/도약/착지(초) | 로컬 도약 높이 | 먼지 개수 |
| --- | --- | --- | --- | --- |
| SlimeSmall | 1 | 0.15 / 0.5 / 0.2 | 1 | 20 |
| SlimeMedium | 1 | 0.15 / 0.3 / 0.12 | 0.75 | 25 |
| SlimeLarge | 1 | 0.15 / 0.3 / 0.12 | 0.5 | 30 |

사용자의 작은 슬라임은 더 높게, 중형은 그 사이, 대형은 기존 높이 유지라는 외형 의도를 반영한다. 주기는 Inspector 값으로 조정한다. 도약 높이는 부모 Scale에 영향을 받으며 실제 공중 충돌을 만드는 3D 점프는 아니다.

### 착지 먼지와 반복 생성 비용

먼지 이미지는 공통으로 쓰고, 입자 수·흩날림 속도로 크기와 착지 강도를 표현했다. Dust는 Visual 자식이 아니라 월드의 지면 위치에서 재생해 몸체의 압축/도약을 따라 움직이지 않게 했다. 힘은 실제 3D 충돌값이 아닌 현재 점프 곡선의 높이/시간에서 산출한 연출값이다.

최초 Instantiate/Destroy 방식은 반복 착지에서 생성 비용이 우려됐다. 공용 ObjectPool로 전환해 사전 생성·비활성화·재사용하고 완료 콜백으로 반환한다. `_isInUse=true` 누락은 반환을 막을 수 있어 지적했고 사용자가 보완했다. 씬에 공용 풀이 없을 때의 조용한 미재생도 연결 작업으로 해결했다.

[한정 실행 확인](2026-11-06-LANDING-DUST-POOL-CHECK.md)에서 실제 슬라임 40마리와 먼지 총 40개 유지·반환을 확인했다. [별도 성능 시험](2026-11-06-DUST-POOL-PERFORMANCE.md)의 10배 부하에서는 호출 구간 CPU가 약 159→30μs/효과, 측정 중 생성이 2,100→162개로 줄었다. 5배·10배는 현 보관 한도보다 큰 동시 수요로 추가 생성이 있었다. 게임 전체/FPS가 같은 비율로 개선됐거나 GC가 없어졌다는 뜻은 아니다.

### 아직 해결하지 않은 전투 연결

가까운 적 조회 함수와 Player.Target은 작성했지만 Player의 검색 타이머가 감소하지 않고 씬 Spawner 연결도 비어 있다. PlayerAttack은 별도의 빈 대상을 사용한다. 따라서 생성된 적을 찾아 회피·공격하고 처치 후 다음 대상으로 이어가는 전체 흐름은 미완료다. [현황](README.md)의 세 수정 항목을 먼저 확인한다. 대화에서 해결안을 제시한 사실과 실제 코드 반영을 구분했다.

## 확인 범위

사용자는 코드를 작성·피드백했고 AI는 코드/직렬화 연결을 정적으로 검토했다. 요청된 MCP 작업에서 외형·도약·먼지 재생과 반환을 관찰했다. 이번 문서화 시점에는 실행을 다시 하지 않았다. 현재 파일 기준과 과거 실측 스냅샷은 서로 다를 수 있다. 모바일 실기기·빌드·전체 전투·장기 안정성은 확인하지 않았다.
