## 문제와 원인

사용자는 다른 코드처럼 직접 읽고 수정할 수 있는 단순한 `StageScenery`를 원한다. 현재 `SpawnGroup`은 연결 확인·후보 추출·위치 선택·간격 검사·생성·크기 변경을 함께 처리한다. 재사용성은 있지만, 처리 흐름을 처음 읽는 사람이 한 번에 이해하기 어렵고 수량 설정도 Groups 내부에 들어가 있다.

현재 호출은 `Stage.Start → EnterStage → StageScenery.Rebuild`다. `Rebuild`는 이전 생성물을 정리하고 각 그룹의 개수를 추첨한다. `SpawnGroup`은 Prefab을 골라 인스턴스를 만들고 그 인스턴스의 크기를 바꾼다. **실행 중 Prefab 원본 에셋을 수정하는 구조는 아니다.** 실제 스테이지 클리어·다음 스테이지 진행 조건은 아직 별도 구현이 없다.

## 위치와 수량에 대해 정리한 내용

- 위치는 맵 전체에서 좌표를 뽑는 방식이 아니라, Inspector에 연결한 후보 지점 중에서 추첨하고 작은 위치 변화를 주는 방식이다. 중앙 공간·외곽 배치를 관리하기 쉬워 현재 방식을 유지한다.
- 자유 좌표 방식은 후보 지점 관리가 줄지만, 경계·중앙 제외·겹침 처리를 별도로 설계해야 한다. 이번에는 전환하지 않는다. 참고 게임의 내부 알고리즘을 확인했다는 의미도 아니다.
- 현재 `SceneryGroup.CountRange`는 직렬화된 `_groups` 안에서 Inspector에 표시된다. 별도의 `_treeCount` 같은 독립 필드는 없다.
- 저장된 4타입의 범위는 모두 `(3, 4)`다. `(6, 6)`은 6개, `(0, 0)`은 배치하지 않음을 뜻한다. 변경값은 다음 `Rebuild` 때 사용하며 후보·간격이 부족하면 실제 수량은 적을 수 있다.

## 선택한 개선 방향과 아직 남은 선택

기능은 유지하면서 **의미 있는 처리 단계로 나눈다.** 파일이나 클래스를 무조건 늘리는 뜻은 아니다.

1. 이전 생성물을 정리한다.
2. 타입별 생성 개수를 정한다.
3. 유효한 Prefab과 후보 지점을 모은다.
4. 후보를 추첨하고 최소 간격에 맞는 위치를 찾는다.
5. 외형을 선택해 생성하고 크기 변화를 준다.
6. 다음 정리를 위해 생성물과 위치를 기록한다.

구체적인 제안은 `_groups` 배열 대신 나무·풀숲·꽃풀숲·꽃 설정을 명시적으로 두고, 수량도 찾기 쉬운 독립 필드로 노출하는 것이다. `GetAvailablePrefabs`, `GetAvailablePoints`, `TryGetPosition` 등으로 긴 처리를 나누되 불필요한 한 줄 함수는 늘리지 않는다. 최종 필드·함수 이름은 사용자 코드 작성 시 정한다.

독립 수량을 `int`로 두면 고정 개수가 되고, `Vector2Int` 범위로 두면 현재의 무작위 개수 기능이 유지된다. **고정값과 범위 중 최종 선택은 미정**이다. 동일 기능 유지가 기준이라면 범위 필드가 맞고, 같은 값을 넣어 고정 수량도 표현할 수 있다.

타입 enum과 switch를 추가하는 방안도 논의했으나, 기존 설정에 매핑을 하나 더 얹어 이해 부담을 늘릴 수 있어 채택하지 않았다. 별도 생성 관리자·풀링·멀티스레드 도입도 이번 개선으로 결정하지 않았다.

## 구현 시 보존할 동작과 연결 위험

- null 참조 제외, 중복 후보 제거, 최소 중심 간격, 위치·크기 변화, 이전 인스턴스 정리를 유지한다.
- 후보를 소비하며 종료하고, 요청 수보다 적게 배치되면 경고한다. 중심 간격 검사는 이미지 전체의 겹침 방지가 아니다.
- 필드 구조를 바꾸면 Stage Prefab의 기존 Groups 연결이 자동 이전된다고 가정하지 않는다. 타입별 Prefab·후보·수량·배율을 대조해 재연결해야 한다.
- 설정을 읽고 고치는 과정이 짧아질 것으로 기대하지만, 아직 리팩터링하지 않았으므로 가독성·CPU·FPS 개선을 실측 결과로 제시하지 않는다.

## AI의 코드 수정 권한을 잘못 판단한 경위

앞선 작업에서 AI는 파일 수정 논의와 “기능 구현·코드적으로 연결” 요청을 C# 직접 수정 허가로 확대 해석했다. 코드 변경이 필요하다는 판단과 그 변경을 실행할 권한을 구분하지 못한 것이 원인이다. 이전 기록의 “코드 연결 범위에서 변경했다”는 표현도 정당한 코드 수정 허가가 있었다는 근거가 되지 않는다.

사용자가 [AGENTS](../AGENTS.md)에 기능 구현 요청도 코드 부분은 제외한다는 문장을 직접 추가했다. 이에 따라 사용자가 코드를 주도하고, AI는 코드 확인·설명·수정 예시를 제공한다. 직접 C#을 수정하려면 별도의 명시적 요청이 있어야 한다. MCP 허가 역시 코드 수정 허가로 보지 않는다. 코드 변경이 필요한 연결 문제는 설명하고, 허가 없이 대신 고치지 않는다.

이 원칙은 배경 배치 구현을 삭제하거나 자동으로 되돌리라는 뜻이 아니다. 현재 코드는 유지하고, 논의한 단순화도 이번 문서화 요청으로 실행하지 않는다.

남은 일은 독립 수량의 표현 결정, 사용자의 코드 정리, 이후 허용된 범위의 Inspector 재연결이다. 다음 기능 착수나 코드 수정 승인은 이번 기록에 포함하지 않는다. 실제 재배치·수량 부족·재진입 동작은 코드 변경 후 확인할 대상으로 남긴다.
