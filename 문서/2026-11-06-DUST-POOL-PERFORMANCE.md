# 먼지 풀링 성능 비교

2026-11-06. 사용자가 그래프·수치 비교와 더 큰 부하를 요청했다. 제품 C# 코드와 Prefab 설정은 변경하지 않고 MCP의 임시 Play 세션에서 측정했다.

![측정 그래프](검증자료/2026-11-06-먼지성능/Comparison.png)

## 조건

- Unity 6000.5.10f1 WindowsEditor, SampleScene, vSync=0, targetFrameRate=-1. 모바일 빌드 측정이 아니다.
- 초당 70회·350회·700회 먼지 재생. 한 효과의 입자 수는 20/25/30을 동일 순서로 반복했다. 위치·파티클 seed·착지 강도·텍스처·셰이더는 두 방식에서 동일하다.
- 슬라임/적/플레이어/공격 스크립트는 임시 세션에서 비활성화해 자연 착지나 공격을 통한 추가 효과를 막았다. 기존 시각 오브젝트와 렌더링은 유지했다. 몬스터 AI 수를 늘린 테스트가 아니다.
- 공통 LandingDust.Play를 호출한다. 생성·삭제 비교용 IObjectPool 어댑터는 매번 Instantiate하고 완료 콜백에서 Destroy한다. 풀링 어댑터는 제품과 같은 ObjectPool의 Get/Release·비활성화·재활성화 방식이다. 어댑터·추적용 컬렉션의 소량 비용도 포함하므로 과거 제품 코드를 그대로 복원한 빌드는 아니다.
- 풀은 40개 예열, 비활성 보관 상한 64. 각 회차에 1초 워밍업과 0.45초 대기 후, 3초간 210/1,050/2,100회 재생하고 마지막 반환을 포함하도록 약 0.5초 추가 관찰했다.
- 부하별 순서는 생성/풀/풀/생성/생성/풀(ABBAAB), 각 3회 시도했다. 첫 기본 부하 생성 회차는 워밍업 반환 70회가 측정에 섞여 제외했다. 따라서 기본 생성은 유효 2회, 나머지는 3회다. 그래프는 회차 지표의 중앙값과 최솟값~최댓값이다.

## 수치

| 재생 부하 | 요청·반환 동기 CPU, 생성→풀 | 측정 중 새 오브젝트, 생성→풀 | 프레임 간격 p95, 생성→풀 |
| --- | --- | --- | --- |
| 1배: 70회/초 | 210.47 → 27.52 μs/효과 | 210 → 0개 | 1.63 → 1.56 ms |
| 5배: 350회/초 | 176.33 → 28.89 μs/효과 | 1,050 → 49개 | 1.96 → 1.74 ms |
| 10배: 700회/초 | 159.30 → 29.97 μs/효과 | 2,100 → 162개 | 2.99 → 1.97 ms |

동기 CPU는 Get/Instantiate·위치/seed 설정·재생과 완료 시 Release/Destroy 호출을 Stopwatch로 누적한 뒤 요청 수로 나눈 값이다. 실제 Unity의 지연 Destroy 처리와 이후 렌더링·물리 비용은 이 값에 모두 포함되지 않는다. 전체 프레임은 Time.unscaledDeltaTime 기반이며 GPU 시간이나 CPU PlayerLoop 시간 그 자체가 아니다. p95는 프레임 간격의 95번째 백분위수다.

10배 조건의 요청·반환 동기 CPU는 약 81.2% 감소했다. 이는 게임 전체 CPU 또는 FPS가 그만큼 개선됐다는 뜻이 아니다. 기본 부하에서 p95 차이는 작고, 회차 범위도 겹치므로 눈에 띄는 프레임 개선을 확정하지 않는다.

5배·10배에서는 풀링에도 추가 생성이 발생했다. 워밍업 후 보관 상한 64개만 남은 상태에서 더 많은 동시 재생이 필요하기 때문이다. 현재 예열/보관 설정이 모든 부하에서 생성 0을 보장하지 않음을 보여준다. 제품의 수량을 자동으로 늘리지는 않았다. 풀 40개 최초 예열 비용의 회차 중앙값은 약 5ms였으며 반복 재생 CPU 표에서 제외했다.

## 메모리 해석

Unity ProfilerRecorder의 `GC Allocated In Frame` 평균은 기본 부하 약 9.03→9.01 KiB/프레임, 5배 9.21→9.03, 10배 9.72→9.08로 관찰됐다. Editor·계측·다른 프레임 작업까지 포함하므로 먼지 단독 할당량으로 해석하지 않는다. 프레임당 값은 초당 처리량과도 다르다.

GC.GetAllocatedBytesForCurrentThread는 모든 호출 구간에서 0을 반환했다. 별도 1MiB byte 배열 할당 대조에서도 0이었으므로 이 카운터는 본 환경에서 유효하지 않은 것으로 처리했다. 원시 결과에는 0이 남지만 요약·CSV에서는 무효값으로 비웠다. GC 0이나 먼지 무할당을 주장하지 않는다. GC 수집 정지 시간은 별도 측정하지 않았다.

## 결과의 제한과 보존

- 시험 중 Script 변경에 따른 것으로 보이는 Stage.cs 7행 CS1519 컴파일 오류가 종료 시 Console에 있었다. 당시 파일에는 미완성 `private` 선언이 있었다. 수정하지 않았다. 측정은 이미 진입한 Play의 마지막 성공 컴파일 상태에서 완료됐다. 오류 발생 시점과 컴파일 작업의 CPU 영향까지 배제하지 못했으므로 특히 전체 프레임 수치는 이번 세션의 참고 관찰이다. 편집 중 소스 지문이 실행 어셈블리와 완전히 일치한다고 주장하지 않는다.
- 종료 후 재확인에서는 Stage.cs의 미완성 선언이 제거되어 있었다. 에이전트가 수정한 것은 아니며 그 이후 성능 시험을 다시 실행하지 않았다.
- 측정용 코드의 첫 메모리 내 컴파일은 참조 경로 길이/중복 문제로 실패했다. 참조를 제한하고 /nostdlib로 재시도한 뒤 실행했다. 제품 컴파일 설정·패키지는 변경하지 않았다.
- 프레임 스파이크 제거·모바일 실기기·장시간 메모리 안정성·통계적 유의성을 검증한 것은 아니다. Editor 검사·백그라운드 부하의 영향을 받는다.
- 종료 시 Play를 끄고 runInBackground=false, timeScale=1로 복원했다. 임시 컴포넌트와 비활성화는 Play 종료로 제거됐다. 씬은 dirty=true였으며 사용자 미저장 상태를 버리거나 저장하지 않았다.
